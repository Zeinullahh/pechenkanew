# Silence AI

## Руководство пользователя Server Security

Инструкции для конечных пользователей по регистрации, установке, защищенному доступу, мониторингу безопасности и управлению политиками.

> **ДОКУМЕНТАЦИЯ ДЛЯ КЛИЕНТОВ**
> Используйте это руководство для регистрации сервисов, установки нативной версии Server Security, настройки управления доступом, анализа инцидентов и мониторинга защиты серверов.

Версия 1.0 • октябрь 2026 г.

# Как пользоваться этим руководством

Это руководство предназначено для администраторов и уполномоченных операторов Silence AI Server Security. В нем рассматриваются действия, доступные в клиентском интерфейсе, и проверки, которые необходимо выполнить, прежде чем полагаться на изменение защиты или управления доступом.

> **Важный принцип эксплуатации**
> Регистрация, установка пакета, регистрация сервера в системе, настройка политик и активная защита — отдельные этапы. Если параметр отмечен как ожидающий, не полагайтесь на него, пока панель не сообщит об активации.

# 1. Перед началом работы

Перед началом работы подготовьте следующие сведения и права доступа:

- Учетную запись Silence AI с доступом к Server Security.
- Домен сервиса или имя сервера, который планируется зарегистрировать.

- Сетевое подключение целевого сервера к Silence AI.
- Права администратора на целевом сервере Linux для нативной установки.

- Для регистрации Hosted: IP-адрес назначения и разрешение на изменение веб-сайта и DNS.
- Для регистрации Self-Hosted: URL вышестоящего сервиса и утвержденную в организации процедуру развертывания.

| **Поддерживаемая нативная цель**       | **Пакет** |
|----------------------------------------|-----------|
| Ubuntu Server 22.04 или 24.04 LTS, amd64 | DEB     |
| Fedora Server 44, x86_64               | RPM       |

> **Оплата Hosted**
> Защита трафика Hosted оплачивается по фактическому использованию. Прежде чем полагаться на нее, убедитесь, что на счете достаточно средств.

# 2. Вход и открытие Server Security

1.  Откройте панель администрирования Silence AI и выберите Log in.

2.  Пройдите MFA учетной записи, используя текущий шестизначный код приложения-аутентификатора.

3.  Откройте Server Security, затем выберите Servers.

В каждой строке сервера могут быть доступны действия Install, Setup / recovery и Open Security. Доступное действие зависит от текущего состояния регистрации сервера.

# 3. Регистрация сервиса

## 3.1 Выбор Hosted или Self-Hosted

| **Тип развертывания** | **Когда использовать**                                 | **Обязательные поля** |
|-----------------------|--------------------------------------------------------|-----------------------|
| Hosted                | Трафик будет защищен с помощью сервиса Hosted.          | Domain + IP Address   |
| Self-Hosted           | Сервис работает в вашей среде.                          | Domain + Upstream URL |

> **Регистрация — не установка**
> Создание записи сервиса Hosted или Self-Hosted не устанавливает нативный пакет Server Security и не регистрирует сервер Linux в системе.

## 3.2 Создание записи сервиса

4.  Выберите Register new agent.

5.  Выберите Hosted или Self-Hosted и перейдите к этапу ввода данных агента.

6.  В поле Domain укажите только имя хоста, без пути URL.

7.  Для Hosted введите IP Address. Для Self-Hosted введите Upstream URL.

8.  Выберите Register.

## 3.3 Hosted: подтверждение владения и маршрутизация трафика

В процессе регистрации отображаются два отдельных элемента: метатег веб-сайта для подтверждения владения и A-запись для маршрутизации трафика Hosted.

9.  Добавьте предоставленный метатег внутрь HTML-элемента \<head\> веб-сайта.

10. Опубликуйте изменение и убедитесь, что веб-сайт общедоступен по зарегистрированному домену.

11. В диалоговом окне регистрации выберите Verify Domain Ownership и убедитесь, что появилось сообщение Verification successful!.

12. Добавьте отображаемую A-запись в DNS для маршрутизации трафика Hosted.

13. После распространения DNS убедитесь, что веб-сайт по-прежнему доступен по нужному домену.

> **Если подтверждение не удалось**
> Проверьте написание домена, общедоступность, размещение метатега и обработку хоста прокси-сервером/CDN, затем используйте Redo verification.

## 3.4 Развертывание Self-Hosted

После создания записи сервиса Self-Hosted выполните утвержденную процедуру развертывания, предусмотренную для вашей среды. Нативная установка Server Security остается отдельным действием Install в таблице серверов.

14. Выберите Install для целевого сервера.

15. В разделе 1. Choose a native package выберите операционную систему и архитектуру, соответствующие серверу.

Используйте имя файла, команду установки и значение SHA-256, отображаемые в вашей панели. Типичные команды выглядят следующим образом:



> **Целостность пакета**
> Для пакетов RPM не отключайте проверку подписи и следуйте утвержденной процедуре работы с ключами подписи. Не получайте ключи подписи из неутвержденных источников и не обходите проверку пакетов.

## 4.2 Регистрация сервера в системе

18. В диалоговом окне установки откройте 3. Enroll interactively.

19. На нужном сервере выполните sudo silence-server enroll.

20. Выберите Generate enrollment code.

21. Вводите отображаемый код только в запросе регистрации на нужном сервере.

22. Не закрывайте диалоговое окно установки во время выполнения этапов подготовки.

> **Безопасность кода регистрации**
> Коды регистрации одноразовые, действуют не более 15 минут и никогда не должны копироваться в заявки, документацию, чаты или историю командной оболочки.

Во время подготовки в диалоговом окне могут отображаться такие этапы, как Enrollment in progress, Verified release ready, Installing security stack, Installing core protection, Core check completed, Installing sensors и Installation complete.

## 4.3 Восстановление и повторная регистрация

Для сервера, уже отображаемого как зарегистрированный, действие Setup / recovery может предоставлять варианты Re-enroll server и Generate recovery code. Используйте восстановление только для нужного сервера и сохраняйте независимый способ доступа администратора на протяжении восстановления, связанного с доступом.

## 4.4 Подтверждение защиты

23. Выберите Open Security для сервера.

24. Откройте Overview и выберите Refresh.

25. Проверьте Server protection, Provisioning, Sensor health и Guard access security.

26. Убедитесь, что текущее состояние и последние данные телеметрии соответствуют ожидаемой защите.

> **Ожидание активации**
> Если в Policy отображается Saved · pending activation, конфигурация сохранена, но ее пока нельзя считать активной.

# 5. Состояния защиты

| **Состояние**          | **Значение**                                                                                                      | **Что делать**                                                               |
|------------------------|-------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------|
| ACTIVE                 | Основная защита доступна согласно отчету.                                                                         | Отдельно проверьте состояние дополнительных датчиков и политик.              |
| DEGRADED               | Основная защита может оставаться доступной, но один или несколько показателей работоспособности или покрытия требуют внимания. | Прочтите причину и проверьте Sensors.                          |
| FAILED                 | При подготовке или работе основной защиты произошел сбой.                                                         | Прочтите сообщение об ошибке и следуйте инструкциям по устранению неполадок. |
| PENDING                | Установка, подготовка или активация политики не завершена.                                                        | Дождитесь завершения; не считайте изменение активным.                        |
| CONFIGURATION REQUIRED | Панели нужны дополнительные сведения для подтверждения работоспособности основной защиты.                         | Подтвердите регистрацию и выполните отображаемое требование.                 |
| REMOVED                | Нативная защита удалена или больше не отображается в отчетах.                                                     | Используйте поддерживаемую процедуру Setup / recovery, если она доступна.    |

На карточках датчиков могут отдельно отображаться состояния Healthy, Degraded, Failed, Disabled, Unsupported, Needs configuration, Telemetry stale или No telemetry.

# 6. Настройка MFA и защищенного доступа

**Доступ по портам:** цель раздела 10 — независимая проверка каждого порта. MFA может временно открыть подходящие порты, но не обходит запрет страны/IP на другом порту; вход в службу обязателен. Прежнее групповое открытие не доказывает работу независимой проверки.

## 6.1 MFA учетной записи

27. Во время регистрации учетной записи откройте Set up 2FA.

28. Отсканируйте QR-код или введите секретный ключ в приложение-аутентификатор TOTP.

29. Введите текущий шестизначный код и выберите Verify and finish.

30. При последующих входах используйте текущий код приложения-аутентификатора.

> **Защита секретов MFA**
> Никогда не передавайте секрет аутентификатора, QR-код или код восстановления другому лицу. При потере доступа к аутентификатору воспользуйтесь утвержденным в вашей организации каналом восстановления учетной записи.

## 6.2 MFA для доступа к серверу (SSH 2FA / Port Guard)

Элемент управления SSH 2FA защищает настроенные TCP-порты как группу; его действие не ограничивается SSH-портом 22 и не распространяется на UDP.

> **Перед изменением управления доступом**
> Сохраняйте независимый сеанс администратора или проверенный способ восстановления, пока не будет подтвержден доступ из нужной исходной сети.

31. В таблице серверов нажмите значок карандаша/редактирования.

32. В Agent configuration добавьте или удалите защищенные TCP-порты, затем выберите Save. Номера портов должны быть целыми числами от 1 до 65535.

33. В строке сервера включите SSH 2FA, чтобы открыть настройку 2FA SSH Guard.

34. Отсканируйте QR-код или введите Manual entry key в приложении-аутентификаторе.

35. Перед продолжением сохраните все восемь Backup / Recovery Codes. Каждый код одноразовый.

36. Выберите Next — Verify Code, введите текущий шестизначный код и выберите Verify.

37. Убедитесь, что появилось сообщение 2FA verified successfully!, выберите Done, затем снова откройте Agent configuration и проверьте нужные порты и параметр доступа.

## 6.3 Аутентификация с помощью Port Guard

38. Откройте адрес Port Guard, предоставленный для вашего развертывания, из той же исходной сети, из которой будет выполняться подключение к защищенному сервису.

39. Введите текущий шестизначный код приложения-аутентификатора или один неиспользованный резервный код.

40. Выберите Unlock Ports.

41. Когда на странице появится сообщение об открытии портов, незамедлительно повторно подключитесь к защищенному сервису.

Настроенные защищенные TCP-порты авторизуются вместе на временный период доступа. Отображаемая длительность является определяющей; создаваемое значение по умолчанию — 60 секунд. Для защищенного сервиса по-прежнему требуются его собственные учетные данные.

> **Одна исходная сеть**
> Браузер, используемый для Port Guard, и клиент SSH, базы данных или приложения должны определяться как подключенные из одной исходной сети. При смене сети может потребоваться повторная аутентификация.

# 7. Использование консоли Server Security

**Network access:** раздел 10 описывает отдельную страницу, выбор сервера/порта, глобус, список и управление правилами. Жесты и кнопки ещё не проверены в реальном браузере; ориентируйтесь на фактические надписи вашей установки.

|-------------|------------------------------------------------------------------------------------------------------------------|

| Incidents   | Коррелированная активность безопасности для анализа.                                                            |
| Responses   | Записи и результаты автоматических ответных действий.                                                           |
| Sensors     | Работоспособность датчиков и представления обнаружений.                                                         |

# 8. Анализ инцидентов и ответных действий

**Разные действия:** **Shut down session** отключает существующее соединение; **Blacklist IP address** сохраняет постоянный запрет новых соединений в своей области. Автоматическая реакция может быть временной и подчиняться другим правилам. Запрос или сохранение не подтверждает отключение либо применение.

## 8.1 Инциденты

Выберите инцидент, чтобы открыть Incident details. Проверьте серьезность, сводку, сведения об источнике, если они доступны, Timeline, Evidence и Technical details.

| **Действие**       | **Результат**                                                        |
|--------------------|----------------------------------------------------------------------|
| Mark investigating | Изменяет состояние проверки инцидента, указывая на активное расследование. |
| Resolve            | Указывает, что проверка инцидента завершена.                         |
| Dismiss            | Указывает, что дальнейшая работа с инцидентом не планируется.        |

> **Состояние инцидента — не устранение последствий**
> Изменение состояния проверки инцидента само по себе не удаляет вредоносное ПО, не прекращает действия злоумышленника и не восстанавливает скомпрометированный сервер.

## 8.2 Ответные действия

| **Состояние**                                      | **Значение**                                                                  |
|----------------------------------------------------|-------------------------------------------------------------------------------|
| REQUESTED / OBSERVED / SHADOW_APPROVED / APPROVED  | Действие зарегистрировано или одобрено для оценки; применение не подтверждено. |
| APPLIED                                            | Ответное действие зарегистрировано как примененное в отображаемой области.    |
| EXPIRED                                            | Временное ответное действие больше не активно.                                |
| REVOKED                                            | Ответное действие отозвано.                                                    |
| FAILED                                             | Запрошенное действие не завершилось успешно.                                  |
| SUPPRESSED                                         | Ответное действие не применялось согласно соответствующей политике.           |

Рассматривайте источник, действие и область, причину, состояние, время начала и истечения вместе. Блокировка новых подключений не обязательно прекращает уже установленное соединение.

# 9. Настройка политики безопасности

**Разные списки:** **Trusted IPs** относится к автоматическим реакциям, **Allowed IPs / CIDRs** — к доступу Port Guard, явные блокировки могут действовать шире. Это не **Always Allow** и не **Always Block** раздела 10. Старые правила требуют согласования при переносе; HTTP-список аккаунта не превращается автоматически в запрет SSH/Kubernetes.

## 9.1 Режим автоматического реагирования

| **Режим** | **Поведение**                                                                                                     |
|-----------|-------------------------------------------------------------------------------------------------------------------|
| Observe   | Регистрирует подходящие решения без автоматического применения.                                                   |
| Shadow    | Оценивает подходящие обнаружения без применения временных блокировок.                                             |
| Enforce   | Может применять одобренные временные блокировки IP, когда активны политика и условия обнаружения.                |

Обычный начальный режим после установки — Shadow. Чтобы использовать Enforce, выберите Enforce, просмотрите Enable automatic enforcement? и подтвердите действие с помощью Enable Enforce. Enforce применяется только к подходящим обнаружениям.

## 9.2 Доверенные IP-адреса

42. Откройте Policy → Trusted IPs.

43. Введите Trusted IP or CIDR и, при необходимости, Description.

44. Выберите Add trusted source.

45. Используйте Remove для удаления записи или Move to block для преобразования ее в явную блокировку.

Trusted IPs освобождает источник от подходящих автоматических блокировок. Это не позволяет обходить MFA, ограничения по странам, Allowed IPs / CIDRs, учетные данные сервисов и другие средства управления доступом.

## 9.3 Разрешенные IP-адреса и CIDR

46. Нажмите значок карандаша/редактирования в строке сервера.

47. В Agent configuration введите отдельные адреса IPv4/IPv6 или диапазоны CIDR в поле Allowed IPs / CIDRs (через запятую).

48. Выберите Save и снова откройте диалоговое окно, чтобы убедиться, что панель сохранила значение.

Если сохраненный список пуст, проверка адреса Port Guard позволяет всем источникам перейти к аутентификации. Если список не пуст, продолжить могут только соответствующие адреса или диапазоны.

## 9.4 Явные блокировки

49. Откройте Policy → Explicit blocks.

50. Введите Blocked IP or CIDR, обязательное значение Reason и необязательное Explicit block expiry.

51. Выберите Add explicit block.

52. Используйте Remove для удаления записи. Чтобы исправить запись, удалите ее и создайте новую.

> **Не допускайте блокировки администратора**
> Перед добавлением блокировки проверьте адреса администраторов, мониторинга, NAT и общие адреса, которые могут использовать тот же исходный IP-адрес или CIDR.

## 9.5 Датчики и Suricata

В Policy → Sensor state могут отображаться переключатели Inventory, File Integrity, Security Configuration, YARA-X, CrowdSec, Falco и Suricata.

Для Suricata откройте Policy → Suricata monitored interface, выберите отображаемый вариант или введите проверенный интерфейс, например ens3, затем выберите Save interface. После изменения убедитесь, что поступает актуальная телеметрия Suricata.

# 10. Сетевой доступ, глобус и активные соединения

**Требования от 2026-10-06.** Раздел описывает требуемое поведение, а не подтверждённую работу в реальной среде. Раньше глобус показывал веб-трафик, ограничения по странам были раздельными, а завершение соединения недоступным. Код CMC/Guard теперь содержит страницу Network access, правила по серверу и порту, подписанное обновление Guard, разрешение nftables по портам, снимки TCP-соединений в сетевом пространстве имён хоста Linux и подписанные команды адресного отключения. В `NETWORK_ACCESS_NET_CHECKLIST.md` указаны статические, модульные и кросс-сборочные проверки. Миграция БД, реальные соединения Linux/Kubernetes, SSH на 2525, действия в браузере, сохранение после перезапуска и сквозное подтверждение агента по предоставленным материалам не проверены. Сохранённое правило остаётся ожидающим, пока агент не подтвердит его ревизию; постановка команды в очередь не означает подтверждённого отключения.

## 10.1 Назначение и область действия (NET-01)

CMC должен объединить 3D-глобус, списки стран, окно блокировки и выдвигаемую вверх панель для контроля настроенных защищённых TCP-портов. **Сетевой сеанс** — реально активное TCP-соединение с наблюдаемого исходного IP-адреса на настроенный порт управляемого сервера. Если SSH работает на порту **2525**, соединение видно, пока оно активно; порт 22 не подразумевается всегда. Это относится и к настроенным конечным точкам Kubernetes, и к другим защищённым TCP-службам. Название службы берётся из конфигурации или проверенных данных. TCP-соединение Kubernetes само по себе не указывает пользователя, оболочку пода или отдельную операцию `kubectl exec`; закрытие мультиплексированного соединения может затронуть несколько операций. Посещения сайтов, HTTP-запросы, вход в браузер, user agent и число уникальных IP в веб-журнале не являются сетевыми сеансами. Независимые функции хостинга, веб-аналитики, регистрации и оплаты сохраняются.

## 10.2 Выбор сервера и порта (NET-02)

Перед просмотром или изменением показывать выбранный сервер и защищённый TCP-порт. У каждого порта могут быть свои режим и список стран; правило порта 2525 не меняет другой порт. Общий вид **All protected ports** должен обозначать смешанные правила. Фильтры и выбор согласованно обновляют глобус, списки и сеансы. Постоянные списки **Always Allow** и **Always Block** относятся к настроенным защищённым портам выбранного сервера, а не автоматически ко всему аккаунту или посторонним портам.

## 10.3 Окно и списки (NET-03)

Первый ряд: **Countries** и **IP addresses**. Для **Countries** второй ряд: **Blacklisted** и **Whitelisted**, поиск, добавление и удаление стран, а также отдельный переключатель **Blacklist mode / Whitelist mode**. Просмотр списка не переключает режим. Явно выбранные страны и их отображаемое дополнение должны быть понятны для выбранного порта. Для **IP addresses** второй ряд: **Always Block** и **Always Allow**. В каждом списке есть **+**, простое поле IP, сохранённые адреса и удаление. Оба списка действуют одновременно независимо от вкладки и режима. Принимать отдельные IPv4/IPv6, нормализовать эквивалентные записи, не допускать дубликаты; JSON, отпечатки браузера, связки IP с пользователем и обязательный CIDR не нужны.

## 10.4 Режимы стран (NET-04)

| Режим | Явно выбранные страны | Все прочие известные страны |
|---|---|---|
| **Blacklist mode** | Заблокированы | Разрешены при соблюдении IP-правил и аутентификации |
| **Whitelist mode** | Разрешены при соблюдении IP-правил и аутентификации | Заблокированы |

Пустой чёрный список не блокирует страны; пустой белый не разрешает ни одну. При смене режима объяснять сохранение или перенос явно выбранных записей; не сохранять показанное дополнение незаметно. Если в **Whitelist mode** выбраны Казахстан и Турция, другие страны отклоняются, если нет действующего IP-исключения. Решение принимается отдельно для каждого порта: запрет одного не запрещает другой разрешённый порт, а разрешение одного не открывает запрещённый. MFA сохраняется. Неизвестную страну показывать как **Unknown country**, не выдумывая геолокацию. Ошибка GeoIP для публичного IP не должна тайно выключать ограничения; в режиме белого списка неизвестный адрес запрещён без **Always Allow**. Частные/локальные адреса обходят оценку страны, но подчиняются IP-ограничениям и MFA; их следует отличать от ошибки определения публичного адреса.

## 10.5 Постоянные IP-исключения (NET-05)

**Always Allow** освобождает наблюдаемый исходный IP от географических ограничений на защищённых портах этого сервера до удаления записи. Пример: Россия заблокирована, но сотрудник работает из России удалённо. Добавление его наблюдаемого IP в **Always Allow** обходит правило страны; MFA и вход в SSH всё равно требуются. Исключение работает и в белом списке без России; удаление восстанавливает обычное решение по стране. **Always Block** запрещает IP даже из разрешённой страны. Оба списка постоянны и действуют одновременно после смены режима. **Always Allow** не обходит учётные данные службы или независимые автоматические меры реагирования. **Trusted IPs** относится к таким мерам и не является синонимом; старые списки разрешённых адресов и явные блокировки требуют согласования. Один нормализованный IP нельзя держать в обоих списках: предложить явный перенос. При противоречивых данных приоритет у блокировки, конфликт сообщается. Порядок: **Always Block**, географическое исключение **Always Allow**, режим страны конкретного порта; затем остаются MFA и аутентификация службы. Общий публичный IP затрагивает всех его пользователей; при смене исходного IP исключение обновляют. По IP нельзя установить личность сотрудника.

## 10.6 Глобус и четыре уровня плотности (NET-06)

Глобус показывает разрешённые/запрещённые страны и активные соединения в выбранной области; разрешённый IP из запрещённой страны должен быть понятен. Цвета политики и плотность сеансов различаются отдельной легендой. Зафиксированные уровни: **0, 1–2, 3–9 и 10+ сеансов**; прежде чем считать их проверенными, сверить с последними данными реализации. Группы маркеров позволяют открыть конкретные IP и соединения, не выдавая страну за точные координаты IP. Обозначать смешанные политики, неизвестные и частные адреса. Прежняя метрика **Active Users** считала недавние IP веб-журнала, а не активные TCP-соединения. У глобуса и списка общие фильтры, время, итоги и свежесть. Подтверждённо закрытые соединения уходят из счёта; офлайн-агент или отсутствие телеметрии означает неизвестно/устарело, а не ноль.

## 10.7 Список сеансов (NET-07)

Проведение вверх открывает список; видимая кнопка раскрытия обеспечивает работу мышью и клавиатурой. Предусмотреть сворачивание. Одна строка соответствует одному соединению; несколько соединений одного IP остаются раздельными. Показывать исходный IP, страну или статус частный/неизвестный, сервер, порт назначения, настроенное название службы при наличии, состояние и реально известное время. **First observed** — первая известная фиксация, не обязательно начало соединения. Поиск, фильтры и навигация должны открывать все строки; размер страницы не является общим числом соединений.

## 10.8 Меню и отключение (NET-08)

Правый щелчок по доступному IP/сеансу глобуса или списка показывает **Shut down session** и **Blacklist IP address**; для касания и клавиатуры нужен равнозначный видимый пункт меню. При нескольких соединениях одного IP явно выбирать конкретное соединение, сервер и порт. **Shut down session** отключает через агента только выбранное реальное соединение: SSH на 2525/22, поддерживаемое соединение Kubernetes или другую защищённую TCP-службу. Оно не останавливает сервер, службу, под или остальные соединения, не обязательно отменяет начатую работу приложения и не запрещает новое подключение. Непосредственно перед действием перепроверять идентификатор соединения; одного IP, имени, приблизительного времени или повторно используемого PID мало. Различать запрос/очередь и подтверждённый исход; отдельно показывать уже закрытое, устаревшее, офлайн, отказ в доступе, отсутствие поддержки, истечение срока и ошибку. Отправка команды не доказывает успех; невозможность безопасно закрыть конкретное соединение следует назвать точно.

## 10.9 Блокировка из сеанса (NET-09)

**Blacklist IP address** добавляет исходный IP в тот же постоянный список сервера **Always Block**. Сначала показывать сохранено/ожидает, затем применено или ошибка по подтверждению агента; запись отображается в окне **IP addresses**. Если адрес уже в **Always Allow**, предложить явный перенос. После применения блокируются новые подключения в области действия; уже открытое соединение от этого не считается завершённым, для него нужно отдельное отключение.

## 10.10 Сохранение, применение и миграция (NET-10)

Единая политика связывает CMC, API/хранилище, доставленную конфигурацию агента и реальное применение. Различать сохранено, ожидает, применено и ошибка, с ревизией и временем; при офлайн-агенте сохранять ожидание. Переживать перезапуск, отклонять устаревшие команды и повторы, проверять права оператора/аккаунта/сервера, вести аудит цели, действия, времени и результата. Старую инструкцию общей HTTP-блокировки стран и отдельный JSON-редактор географии заменить этим общим процессом. Не превращать молча HTTP-список аккаунта в запрет SSH/Kubernetes всех серверов. Существующие нативные и IP-ограничения переносить осознанно, без ослабления защиты и скрытых запретов. Отдельная HTTP-аналитика и прочие функции сохраняются.

## 10.11 Обязательная проверка (NET-11)

Перед объявлением завершения проверить **NET-01**–**NET-11** с файлами, доказательствами и нерешёнными пунктами: независимые порты, включая SSH 2525; оба режима, пустые списки и смена режима; два ряда вкладок и одновременные IP-списки; сотрудник в России в обоих режимах с MFA; приоритет запрета, IPv4/IPv6 и дубликаты; реальные SSH, Kubernetes и обычные TCP-соединения на глобусе и в списке; четыре уровня, совпадающие итоги и устаревшие данные; жест, мышь, клавиатура и меню; отключение ровно одного соединения при общем IP; исходы уже закрыто/устарело/нет прав/ошибка/не поддерживается; постоянная блокировка, подтверждение агента, перезапуск, изоляция аккаунтов и миграция. Одного интерфейса и имитационных данных недостаточно. Недостающие реальные проверки Linux/Kubernetes и браузера отмечать отдельно.

# 11. Просмотр датчиков, инвентаризации, состояния и результатов

## 11.1 Датчики

| YARA-X                              | Признаки шаблонов вредоносного ПО.                |

## 11.2 Инвентаризация и сведения об уязвимостях

В Inventory могут отображаться имя пакета, версия, экосистема, архитектура и время последнего наблюдения. Используйте Search packages для фильтрации клиентской таблицы пакетов. Инвентаризация носит информационный характер; она не обновляет пакеты и не устраняет уязвимости.

> **Осторожно интерпретируйте пустые или устаревшие данные**
> Пустые, недоступные, неизвестные или устаревшие сведения об инвентаризации или уязвимостях не доказывают отсутствие пакетов или уязвимостей на сервере.

## 11.3 Состояние безопасности

Используйте Posture для просмотра результатов Security Configuration Assessment и состояния сведений об уязвимостях. В результатах могут отображаться не пройденные или вернувшиеся проверки и предоставленные рекомендации. Posture — это представление оценки, которое не исправляет сервер автоматически.

# 12. Мониторинг событий и телеметрии

**Свежесть:** журналы доступа и старая метрика **Active Users** не считают активные TCP-соединения. Глобус и список раздела 10 должны использовать общие фильтры, итоги и время. Нет или устарела телеметрия — значит неизвестно/устарело, не ноль.

Откройте Events и используйте доступные фильтры:

- Фильтрация по датчику.
- Фильтрация по типу события с использованием точного типа.

- Фильтрация по серьезности: All severities, critical, high, medium, low или info.
- Используйте Previous и Next для перехода между страницами.

Проверьте название события, источник, тип, доказательства, серьезность, отметку времени и связанный инцидент, если он отображается.

# 13. Устранение неполадок

**Неожиданный доступ:** проверьте сервер и порт, режим страны, реально наблюдаемый исходный IP, **Always Block**/**Always Allow**, старые ограничения и применённую ревизию. При изменении IP обновите исключение. Ожидающее правило, офлайн-агент или устаревшая сессия не подтверждают состояние; запрошенное, просроченное или неподдерживаемое отключение не считается подтверждённым.

> **Первое правило**
> При изменении управления доступом сохраняйте независимый доступ администратора. Записывайте текст ошибок, не содержащий секретов, и никогда не передавайте коды регистрации, секреты MFA, резервные коды, закрытые ключи и содержащие их снимки экрана.

| **Ситуация**                                       | **Рекомендуемое действие**                                                                                                                                                                                                   |
|----------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Не удается установить пакет                        | Убедитесь, что выбранный пакет соответствует ОС и архитектуре, загрузите его повторно, сравните отображаемый SHA-256 и выполните скопированную команду с правами администратора. Для RPM не отключайте проверку подписи.      |
| Истек срок действия кода регистрации               | Создавайте новый код, только если предыдущий не использовался или панель явно разрешает замену. Если код был принят до последующего сбоя, используйте Setup / recovery, когда сервер отображается как зарегистрированный.    |
| Активная защита не подтверждена                     | Откройте Overview и проверьте Server protection, Provisioning, Sensor health и Guard access security. Выполните указания причины состояния PENDING, DEGRADED, FAILED или CONFIGURATION REQUIRED.                              |
| В Policy отображается Saved · pending activation   | Считайте политику сохраненной, но еще не активной. Сохраняйте предыдущую безопасную конфигурацию и доступ администратора до завершения активации.                                                                            |
| Не удается настроить MFA                            | Проверьте время приложения-аутентификатора, используйте текущий шестизначный код, проверьте нужные порты и не закрывайте существующий сеанс администратора.                                                                  |
| Port Guard открывает порты, но сервис недоступен    | Быстро подключитесь повторно, убедитесь, что браузер и клиент используют один наблюдаемый источник, проверьте защищенный порт и учетные данные сервиса, затем Allowed IPs, правила стран, явные блокировки, автоматические ответные действия и сетевую политику. |
| Утрачен доступ к приложению-аутентификатору         | При наличии используйте неиспользованный резервный код, затем следуйте утвержденному в организации процессу восстановления.                                                                                                 |
| Ограничения по IP или странам работают неожиданно  | Определите управляющую функцию, проверьте исходный адрес и порт, приоритет и срок действия правил, а перед добавлением нового правила убедитесь, что администратор не был случайно заблокирован.                              |
| Телеметрия датчика отсутствует или устарела         | Откройте Sensors, проверьте состояние датчика и Last signal, а также параметры, например интерфейс Suricata, если это применимо.                                                                                              |
| Инвентаризация пакетов пуста                        | Используйте Search packages и сопоставьте таблицу пакетов с другими действиями инвентаризации. Считайте пустую таблицу неполными сведениями, а не доказательством отсутствия пакетов.                                        |

# 14. Рекомендации по безопасности и эксплуатации

**Текущие пределы:** в предоставленных материалах нет полной проверки кода раздела 10 на реальных Linux/Kubernetes и в браузере. Временное разрешение MFA требует nftables. Сборщик видит установленные TCP-сокеты только в сетевом пространстве имён хоста выбранного узла, не все поды, узлы или внешние балансировщики. Без идентификатора сокета статус — не поддерживается; слишком большой снимок помечается устаревшим, не полным. Перезапуск, подтверждение и точное отключение ещё требуют проверки.

- Используйте наиболее узкие практически применимые диапазоны IP/CIDR для доверенных и разрешенных источников.
- При включении MFA, явных блокировок или ограничений по странам сохраняйте проверенный способ восстановления доступа администратора.

- Не полагайтесь на сохраненную конфигурацию, пока панель не сообщит о соответствующем активном/работоспособном состоянии и оно не будет подтверждено актуальной телеметрией.
- Считайте обнаружения датчиков свидетельствами для расследования; не предполагайте, что каждое обнаружение было автоматически заблокировано.

- Проверяйте срок действия ответной меры, прежде чем считать автоматическую блокировку все еще активной.
- Не удаляйте вручную файлы или службы безопасности для восстановления, если это прямо не предусмотрено утвержденной эксплуатационной процедурой.
